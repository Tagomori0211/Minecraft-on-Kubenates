## ADR 01: GKEからGCE & Docker Composeへの移行（コスト最適化）

### 背景
- 当初は Pod 単位の課金モデルおよびマネージドサービスの利便性を理由に、プロキシ層として GKE Autopilot を採用して運用していた。
- 稼働後数日で、マネージドクラスタに起因するコストが許容範囲を超えることが判明し、直ちに GKE Standard へ移行した。
- しかし、GKE Standard のシステムコンポーネント（OSやKubernetes自体のオーバーヘッド）によるメモリ消費が大きく、`e2-small`（2GB RAM）1ノードでは Minecraft プロキシ関連の Pod（`nginx-gw`, `velocity`）がリソース不足で `Pending` となり起動できない問題が発生。
- 一時的に `e2-medium`（4GB RAM）へ増強、あるいは DaemonSet + hostPath 等による最適化を行ったものの、GKE 構成全体の維持費用が月額約 ¥19,700 と高コストであった。

### 決定
- プロキシ層において Kubernetes の高度な機能を必要としないことが明らかになったため、GCE の採用を検討した。
- プロキシ層の Kubernetes (GKE) 自体を完全に廃止し、GCE 単一 VM (`mc-proxy-1`, e2-small / 2GB RAM, pd-balanced 20GB, asia-northeast1-b) 上の Docker Compose 構成へ移行した。
- オンプレミスクラスター (k3s) との接続経路として、Tailscale メッシュ VPN を採用し、GCE VM 上で `tailscaled` をホスト側の systemd (kernel mode) で常時稼働させた。

### 結果
- **コストの大幅削減**: クラウド（GCP）側のコストが月額約 ¥19,700 から約 ¥3,680 へと **81% の削減**を達成。
- **リソース効率の向上**: VM 内の Kubernetes 制御プレーンやシステムコンポーネントのメモリオーバーヘッドが消滅し、VM リソース（2GBメモリ）をプロキシおよび中継プロセス（socat 等）に最大限活用可能となった。
- **耐障害性の向上**: シンプルな Docker Compose 起動のため、障害発生時の再起動やトラブルシュートが容易になった。

## ADR 02: BedrockプロキシのL4透過転送(socat)への統一とL7プロキシの廃止

### コンテキスト
- Bedrock Edition（BDS）のプロキシとして、当初 WaterdogPE（L7）や Node.js ベースの `bedrock-relay`（L7）を採用した。
- しかし、以下の致命的な問題が頻発した：
  1. **パケット消失**: マイナーバージョン（プロトコルバージョン）の違いにより、未知の操作パケットがプロキシ層でドロップされ、チェストやドアが開かない等の現象が発生。
  2. **認証情報の消失 (XUID 消失)**: プロキシが Xbox Live 認証の暗号化ペイロードを正しく処理できず、すべての接続プレイヤーの XUID が `Unknown (0)` として転送され、2人目以降のログインが `Already connected`（ゴーストセッション/ID衝突）として弾かれた。
- また、L4プロキシとして Nginx Stream (UDP) を使用した際、Nginx の UDP プロキシ仕様により新しいパケットごとに異なるソースポートが割り当てられ、RakNet（ステートフルなUDPプロトコル）のセッションが数秒で切断された。

### 決定
- L7 プロキシ（WaterdogPE, bedrock-relay）および Nginx Stream (UDP) プロキシを完全に廃止。
- GCE VM 上の Docker Compose にて、`socat` の UDP 透過転送（`UDP4-LISTEN:19132,fork,reuseaddr`）を採用し、オンプレミス側の BDS ポートへ直接中継した。

### 結果
- **完全な互換性**: パケットを一切解析・改変せずにそのまま透過させる（L4 透過）ため、BDS のバージョンアップ時もプロトコル不一致が発生しなくなり、XUID も正常に伝達されて多人数同時接続が可能になった。
- **セッションの維持**: `socat` の `fork` オプションにより、クライアントの接続（ソースIPおよびポート）ごとにソケットをフォークして透過転送するため、RakNet のステートフル接続が破綻しなくなった。

## ADR 03: オンプレk3sメモリ制限に伴うPod再起動ポリシーの厳格化

### 背景
- オンプレミスのリソース（Ryzen 5700G, 64GB RAM）は、当初Lobby（8Gi）, Survival（16Gi）, Industry（30Gi）, Bedrock（8Gi）の各サーバーの要求メモリ予約合計が約 62Gi に達しており、物理的な空きメモリが限界に近い。
- この状態で `kubectl rollout restart` を行うと、Kubernetes は旧 Pod の稼働を維持したまま新 Pod を立ち上げるため、一時的に要求メモリがオーバーコミットされ、OOMKilled によるプロセスクラッシュやノードフリーズが発生する重大なリスクがあった。

### 決定
- `minecraft` namespace のゲーム用 Deployment において、**`kubectl rollout restart` の実行を完全に禁止**した。
- 再起動やマニフェスト更新時は、まず `replicas=0` にスケールダウンして旧 Pod のメモリを完全に解放し、`Terminating` プロセスが消滅したことを確認した後に `replicas=1` にスケールアップする手順をルール化した。

### 結果
- 限界まで切り詰めたメモリ容量であっても、Pod の更新や設定変更時にノードのクラッシュを招くことなく、安全にリリースサイクルを回せるようになった。

### ステータス
- 当初の直接原因であったメモリ逼迫は ADR 05 により緩和済み。
- ゲームサーバーはメモリ使用量の瞬間増加や終了待ちの影響が大きいため、`rollout restart` を避けて `replicas=0 → 1` で更新する運用方針は現在も維持する。OOM Killer 発動時の対応手段としても引き続き有効である。

## ADR 04: Bedrock Server 接続性監視の MOTD 健全性チェック採用

### 背景
- BDS 1.26.x への自動更新時、特定のワールドデータ（`level.dat`）が破損し、`LANBroadcast` フィールドが `0` に書き換わってしまった。
- これにより、BDS は RakNet `UNCONNECTED_PONG` 応答にサーバー名やバージョン等の「MOTD（Server ID 文字列）」を載せなくなった。
- クライアントは MOTD がないためにサーバーを検出できず接続タイムアウトとなったが、従来の監視ツール（itzg/mc-monitor）は単に「UDPポートから Pong 応答があるか」で生存確認を行っていたため、この深刻な接続障害を検知できず17時間放置された。

### 決定
- 監視ツールを Python による自作カスタムエクスポーターに差し替え、単に RakNet の Pong 応答があるかどうかだけでなく、**「返された Pong 応答に正常な MOTD (Server ID) 文字列が内包されているか」** をチェックして `minecraft_status_healthy=1` とする判定ロジックを実装した。
- また、プレイヤーのログイン数 (`minecraft_status_players_online_count`) が長期間ゼロのまま推移している状態をアラート検知の条件に追加した。

### 結果
- クライアント視点での「実際の接続可能性（Discovery 可能性）」に追従した監視ができるようになり、サイレントな接続障害を速やかに検知・対応できるようになった。

## ADR 05: Javaワールド統合に伴う工業エリアのディメンション隔離

### 背景
- 複数ワールドでの運用を行っていたが、単一ノード構成において複数ワールドを維持する必然性が低いと判断し、同一サーバー・同一ワールドに統合する方針へ移行した。
- しかし、同一ワールド上に大規模工業設備を構築すると、大量の Tick 処理によるサーバーのラグ（TPS低下）が一般のサバイバルエリアにまで波及し、同時に配線や機械による景観破壊も課題となっていた。
- 当初は Ad Astra MOD を導入して月面ディメンションを工業地帯にする案があったが、前提 MOD (botarium) が NeoForge 1.21.1 に対応していないためクラッシュし、断念した。

### 決定
- vanilla datapack を使用して、カスタムディメンション `industry` （海面高さを `sea_level: 20` に下げて海面積を極小化した採掘・実用特化のフラットなオーバーワールド型地形）を自前定義した。
- ディメンション間の移動には、追加 MOD 数を最小限に抑えるため `World Portal` MOD のみを採用した。

### 結果
- 多数の MOD の競合リスクを回避しつつ、工業 Tick ラグをディメンション単位で隔離することに成功。
- サバイバル生活エリアの景観と快適なレスポンスを保護し、工業側の自由な設備拡張も実現した。
- 単一 Java ワールド構成への統合により、運用負荷の軽減を実現した。

## ADR 06: エントランスsocatの選定

### 背景
- Bedrock Edition の UDP 通信が L7 プロキシ（Nginx Stream UDP）では正常に中継できないことが ADR 02 で判明し、socat への移行を実施した。また、ADR 05 のカスタムディメンション採用によりマルチワールドの振り分けが不要となった。

### 決定
- 単一ワールド運用への移行により Velocity によるマルチサーバー振り分けが不要となったため、Nginx Stream によるプロキシを廃止し、Java・Bedrock の両エントランス転送を socat に統一した。メモリ消費の削減、障害点の低減、およびクラウドコスト最適化を主な根拠とした。

### 結果
- 転送処理のみに特化したエントランス構成では e2-micro でも十分な性能を発揮できることが確認され、e2-medium から e2-micro へのダウングレードにより大幅なコスト削減を実現した。
- 統合により同一 IP・別ポートで Java/Bedrock 両バージョンに対応する構成が実現し、管理・把握が容易になった。

## ADR 07: Kubernetes（k3s）上でのMinecraft運用

### 背景
- IaC における宣言的管理の一貫性を重視し、Terraform・Ansible・Kubernetes による TAK 構成での統一を目指した。
- バックアップジョブ等を Pod として管理し、実行ログを記録・追跡できる体制を整備することを要件とした。
- 障害発生時の自動再スケジュールによる運用コストの削減を目的として、コンテナオーケストレーションの採用を選択した。


### 決定
- Kubernetes を使用するが、フル機能は不要であるため k3s ディストリビューションを採用。
- クラウド側との接続に Kubernetes ネットワークを使用した場合、コントロールプレーン障害時に監視系が同時に停止するリスクがあるため、クラウド側の監視スタックをクラスタから分離した。
- Minecraft・バックアップ・集計・監視エージェントを同一の宣言的制御面で運用する。
- Minecraft サーバー自体は単一 writer 前提のステートフルワークロードであり、Web アプリケーションのような水平スケールとの相性は高くない。
- その上で、バックアップ・集計・監視エージェント・設定配布を同一の宣言的制御面に載せることを優先し、ワークロード単体のスケーラビリティではなく運用統一性を重視して Kubernetes を採用した。

### 非採用案
- Docker Compose: 単一ホスト上の常駐コンテナ管理には適するが、バックアップ/分析ジョブを含む運用全体を同一制御面で扱いづらい。
- systemd: 依存関係と設定配布の管理が分散しやすく、宣言的管理の一貫性を損なう。

### 結果
- k3s の採用により、軽量な構成を維持しつつ Kubernetes エコシステムの恩恵を享受できた。
- Namespace を分離したことで、将来的なオンプレミスサービスの追加展開に対する拡張性も確保した。

## ADR 08: GCEクラウド側、監視にDocker Composeを採用した理由

### 背景
- IaC による宣言的管理を実現することを要件とした。
- k3s はシステムコンポーネントのオーバーヘッドが大きく、クラウドコスト削減の観点から採用を見送った。
- k3s クラスタから完全に独立した第三者的観測者としての監視層を構築することを目的とした。

### 決定
- k3s クラスタと異なり、コンテナの増減が発生しない構成であるため、宣言的管理が可能な Docker Compose を採用した。
- コンテナ技術を活用しつつ、サービスの乱立による管理の複雑化を避けるため systemd は不採用とした。

### 結果
- 1 秒間隔の高頻度スクレイプを行いながらも e2-small で稼働する軽量構成を実現した。
- 上記のメリットを享受しながら、GCE e2-small 運用によるコスト削減を達成した。
- 完全な独立系監視層の構築に成功。

なお、1 秒スクレイプは Minecraft の TPS・MSPT・プレイヤー数など短時間スパイクの観測価値が高い指標に限定し、ノードメトリクスや Kubernetes メタデータ系は 15〜30 秒間隔として監視負荷を抑制した。

## ADR 09: BigQuery(BQ)の導入

### 背景
- 軽量構成の監視 VM のトレードオフとして、ログ保持期間が最大 14 日に限られる。
- 分析基盤の構築を通じて、データ活用能力をポートフォリオとして示すことを目的とした。
- Looker Studio を用いた長期可視化を実現することを要件とした。

### 決定
- BigQuery を導入した。ただし、監視データをそのまま挿入すると粒度が細かすぎるため、VictoriaMetrics から値を取得し 15 秒平均に集約した上で BQ へ挿入する Pod を k3s クラスタに追加した。
- VictoriaMetrics の保持期間を延長した場合は監視 VM のストレージコストが増大し、かつ分析用途には SQL 基盤が適するため、BQ を採用した。

### 結果
- ノイズを抑えた長期データの蓄積を実現した。
- 本プロジェクト規模のデータ量では BQ の無料枠内に収まり、追加コストゼロを達成した。
- 月単位でのサービス利用状況の把握が可能となった。

## ADR 10: ワールドデータのバックアップ/リストア戦略

### 背景
- Minecraft ワールドはステートフルなデータであり、破損時の影響が大きい。
- Java/Bedrock で保存方式が異なる。

### 決定
- サーバーを適切に停止した上で、Java・Bedrock それぞれに CronJob でバックアップ Pod をスケジュールする。
- 保存先: 別ノードでセルフホスティングする MinIO (S3 互換) へ日次バックアップ。
- 日次バックアップサーバーの障害に備え、GCS へ月次バックアップ。

### 結果
- 通常障害時の RPO: 24時間以内（日次バックアップから復旧）
- バックアップ保存先（MinIO）自体の障害時の最悪RPO: 最大30日（月次GCSバックアップから復旧）
- RTO: 手動復旧で15〜30分

### 今後の改善項目
- ワールド破損時のリストア手順を標準化し、Runbookとして文書化する
- 定期的なリストア演習を実施し、RTO見積もりの妥当性を検証する
